# KAI OMNIPRESENT HOLDING COMMAND OS — Threat Model (§164)

> Deliverable required by spec §164. Grounded in `docs/KAI_OMNIPRESENCE_BASELINE.md`
> (esp. Domain F §75/§76/§77/§78), the §0–§166 spec index, and the real modules in the
> `cyberops` tree (`feat/kai-cyber-operations`). App A = `core.api:app` (top-level `core/`,
> `app.wheellsverse.com`). App B = `backend/app/main.py` (`kai.wheellsverse.com`).
>
> **Every mitigation cites a module that exists on this branch** (verified by grep, this session).
> `test/proof` is marked **existing** (a real `test_*.py` runs it) or **NEEDED** (no test yet —
> maps to a spec cert suite §134/§140/§142/§143/§144/§146/§157). Residual risk is the honest
> gap that survives the current mitigation — §0 #8: never conceal a gap.
>
> **Posture reminder (§0 #12):** everything that grants authority ships **dark**. Autonomy OFF,
> `MONEY_MODE=MOCK`, cyber-ops flag off, no isolated staging. Several residual risks below are
> "acceptable **only while dark**" — they must be re-scored before any authority flag flips.

## 3. KNOWN GAPS — explicit callouts (from baseline, per task)

These are the four the operator asked to be flagged loudest. All are **HIGH residual** and gate specific phases.

1. **§76 — chat/reasoning-context ingestion NOT routed through `scan_for_injection`** (T1, T6).
   The external-**data**/capability-result path is scanned (`capability/results.scan_for_injection` + `sanitize_external_result`, tested). The **chat & reasoning-context** builders (`nai_brain`/`twin` pulling README/logs/PR text into the model prompt) are **not**. A poisoned repo README or log line reaches the model unscanned. → **Phase 5 §76 gap-fill: route the chat-context path through the existing `scan_for_injection`; add the §142 injection suite over that path.**

2. **§6 — `core/wake_word_listener.py` covert always-on mic** (T8).
   Confirmed: it "continuously listens for the wake word NarAI" in a daemon thread. It is a NarAI artifact, not wired here, but there is **no code guard** stopping it being enabled in this context — the mitigation is currently "don't enable it." → **Add an assert-disabled guard for this deployment + a Feature Registry entry (§150) with runtime state OFF, before any voice work (Phase 7). Default privacy mode = PUSH_TO_TALK (§151).**

3. **§71 — `holding.html` zero accessibility (and unaudited escaping)** (T15).
   The main deployed dashboard has **0** aria/role/reduced-motion attributes (verified) and no XSS-rendering test, while `cyber-operations.html` is clean (`esc()` + full ARIA). This is both an a11y failure (§146) and an unsafe-rendering exposure on the highest-traffic surface. → **Phase 6: port `esc()` + ARIA/focus/reduced-motion to `holding.html`; add §144/§146 cert.**

4. **No isolated staging environment** (T17, T18).
   Recurring MEMORY blocker. "Staging" today is an `APP_ENV` convention on shared infra, not an isolated environment. Every authority-enablement step (A2+, execution, real money) requires a hosted-edge cert gate that has **nowhere to run**. → **Operator must stand up isolated staging before ANY authority flag flips. This is the program's top external blocker.**
