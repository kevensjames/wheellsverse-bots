## 1. HMAC Token Math — Why Unsubscribe Links Can't Be Forged

### The threat model

A cold-email recipient gets a unique link like:

```text
https://app.wheellsverse.com/u/Y2hhcmxlc0BwZWxoYW1ob3VzZXJlc29ydC5jb218MTc4MTI3NzMwMVLQ-dNHlJYegwq0AwvfC40
```

If anyone could guess these links, they could:
- Unsubscribe ANY email address by visiting `/u/<their-guess>`
- Mass-unsubscribe competitors' prospects
- Trigger CAN-SPAM violations by un-suppressing then re-emailing

So the token must be **unforgeable** by anyone without the server's secret.

### How HMAC solves this

HMAC = Hash-based Message Authentication Code. It's a cryptographic function that takes:

```text
HMAC(secret, payload) = hash
```

Two key properties:
1. **Same inputs always produce same hash** → server can re-compute and verify
2. **Without knowing the secret, you CANNOT produce a valid hash for any payload** → attackers can't forge

The `SITEBOOST_UNSUBSCRIBE_SECRET` env var is a 256-bit random value (32 bytes, base64-encoded to 44 chars). With that secret in hand:

- Generator: `sig = HMAC-SHA256(secret, "email|timestamp")[:16 bytes]`
- Verifier: re-computes `HMAC-SHA256(secret, "email|timestamp")` and constant-time-compares

If sig matches → the link was generated by our server → trustworthy → process the unsubscribe.
If sig doesn't match → forged or corrupted → return "Link not recognized".

### Why 16 bytes of HMAC instead of 32?

A full SHA-256 HMAC is 32 bytes (256 bits). We truncate to 16 bytes (128 bits) because:

- Brute-forcing a 128-bit unforgeable signature requires ~10^38 operations
- That's well beyond any realistic attacker for an opt-out token
- Shorter token = shorter URL = better UX in email body

### The bug we hit and fixed

Original layout was `payload + "|" + sig` — using `|` as a separator between text and binary.

**Problem**: a random 16-byte HMAC has a 6.25% chance per byte of containing `0x7C` (the `|` character). Across 16 bytes, that's ~63% probability of AT LEAST ONE `|` appearing in the signature.

When the verifier did `raw.rsplit("|", 1)`, it would split INSIDE the signature about 63% of the time → wrong split → "Link not recognized" for valid tokens.

**Fix**: positional layout with NO delimiter:
```text
token bytes = payload || sig    (sig is ALWAYS exactly 16 bytes at the end)
verify: sig = token[-16:], payload = token[:-16]
```

Now: 100% of valid tokens verify correctly. Tested with 100 emails — zero failures.

### Implementation

```python
# core/cold_outreach.py
def make_unsubscribe_token(email: str) -> str:
    secret = _unsub_secret()
    ts = str(int(time.time()))
    payload = f"{email}|{ts}".encode()
    sig = hmac.new(secret, payload, hashlib.sha256).digest()[:16]
    return base64.urlsafe_b64encode(payload + sig).rstrip(b"=").decode()

def verify_unsubscribe_token(token: str) -> Optional[str]:
    pad = "=" * (-len(token) % 4)
    raw = base64.urlsafe_b64decode(token + pad)
    if len(raw) < 16 + 3:
        return None
    payload, sig = raw[:-16], raw[-16:]
    expected = hmac.new(_unsub_secret(), payload, hashlib.sha256).digest()[:16]
    if not hmac.compare_digest(sig, expected):
        return None
    email, _ts = payload.decode().rsplit("|", 1)
    return email
```

`hmac.compare_digest` is a constant-time comparison — prevents timing attacks where an attacker could measure how many initial bytes matched to learn the secret.

## 2. Instantly Campaign Template — Exact Configuration

Instantly is the actual mail sender. SiteBoost only adds leads + variables; Instantly's campaign template controls what each touch looks like.

### Required campaign settings

In Instantly UI → Campaigns → Create New:

**Step 1 — Campaign Settings:**
- Name: `SiteBoost Outbound — Local Business`
- Account: `siteboost@hello.wheellsverse.com` (or however you configured the sender)
- Schedule: Send M-F, 9-11 AM and 2-4 PM recipient local time
- Daily limit: Start at 5/day, grow per warmup schedule

**Step 2 — Sequence (3 touches):**

#### Touch 1 — Day 0

Subject:
```text
{{first_name}} — quick fix idea for {{company_name}}
```

Body:
```text
Hi {{first_name}},

I noticed your site has some issues that are likely costing you visitors. Built you a quick fix preview:

  {{personalization}}

That's a working preview, not a mockup. SSL on, mobile-first, fast. Yours to keep either way.

If you'd want me to put this live on your own domain with email + hosting included, I do the fix for $297 one-time, $49/mo to keep it running. Most customers see a noticeable bounce-rate drop within a week.

No pressure — the preview is yours regardless. Reply if you want to talk.

— Jay
SiteBoost AI
```

#### Touch 2 — Day 3

Subject:
```text
Re: quick fix idea for {{company_name}}
```

Body:
```text
Hi {{first_name}},

Quick follow-up on the {{company_name}} site preview I sent earlier this week: {{personalization}}

One thing worth knowing — sites with technical issues lose 13-50% of would-be customers depending on the problem.

Want me to launch the fix this week?

— Jay
```

#### Touch 3 — Day 7

Subject:
```text
{{first_name}} — closing the file?
```

Body:
```text
Hi {{first_name}},

Last note from me on the {{company_name}} site — I assume the timing isn't right and I'll close the file on this one.

If anything changes, the preview will stay at {{personalization}} for another 30 days.

All the best,
— Jay
SiteBoost AI
```

### Why these templates instead of SiteBoost's per-issue copy?

SiteBoost generates 13 different opener variants based on the SPECIFIC site issue (no-https, timeout, etc.). Instantly's template is the FALLBACK / unified version that works regardless of issue.

**For maximum reply rate**, you have two options:

**Option A — Simple (recommended for first 30 days):**
- Use the generic template above in Instantly
- SiteBoost composes the issue-specific copy and stores it in `04-sequences.json`
- You manually paste the issue-specific opener into Instantly for high-value prospects

**Option B — Multi-campaign (recommended at scale):**
- Create 13 separate Instantly campaigns, one per issue type
- Set `INSTANTLY_CAMPAIGN_ID` dynamically per scan based on the dominant issue
- Requires a small code change to look up the issue → campaign UUID mapping

For your first 30 days, do Option A. Once you have data on which issues convert best, build the multi-campaign mapping in Option B.

### CAN-SPAM footer

Instantly will append its own footer with unsubscribe URL — but SiteBoost ALSO appends our footer with the proper physical address + the HMAC-signed unsub link. Risk: duplicate footers.

Fix: in Instantly campaign settings → Footer → set to BLANK. SiteBoost's footer is the only one.

## 3. Chain Filter — How It Works + How to Extend

### Current behavior

`places_scanner.py` defines a set of lowercase substring patterns:

```python
CHAIN_BLOCKLIST = {
    "walmart", "target", "costco", "starbucks", ... (60 brands)
}

def _is_chain(name: str) -> bool:
    n = name.lower()
    return any(brand in n for brand in CHAIN_BLOCKLIST)
```

Substring matching is intentional — catches "Walmart Supercenter", "Walmart Pharmacy", "Walmart Neighborhood Market" all from the single entry "walmart".

### How to add a new brand

Three rules for new entries:

1. **Always lowercase** — match is case-insensitive on the name
2. **Use the SHORTEST unique substring** — "mcdonald" catches "McDonald's Restaurant" and "McDonalds" both
3. **Avoid generic words** — "kitchen" would falsely match every local restaurant with "Kitchen" in name

### What if a real local business has a chain-sounding name?

Edge case: "Chase's Plumbing" would match "chase" (intended to catch Chase Bank).

Two ways to handle:
1. **Add word boundaries**: change `_is_chain` to use regex `\bchase\b` (matches word "chase" not as substring)
2. **Manual override**: add a `WHITELIST` set for specific business names to ALWAYS allow

For SiteBoost's volume, just accept rare false-positives — they cost you nothing (you just don't email them; you'd see "chains rejected: 8" instead of 7).

## 4. Bad-Website Detection — How to Add New Rules

### Current detection rules (13 categories)

In `places_scanner.py:_probe_website(url)`:

```text
- no-https              → URL not https:// after redirects
- ssl-broken            → SSLError exception
- timeout               → 5-second timeout fired
- connection-failed     → DNS/network error
- http-4xx              → status >= 400
- http-5xx              → status >= 500
- placeholder-or-empty  → response body < 500 bytes
- parking-page          → contains "godaddy", "domain for sale", etc.
- not-mobile-friendly   → missing <meta name="viewport">
- coming-soon           → contains "coming soon", "under construction"
- no-title              → missing <title> tag
```

### How to add a new rule

The probe returns a list of detected issues. Adding a rule = adding one more append.

Each new rule needs three things:
1. **The detection logic** in `_probe_website()`
2. **The opener template** in `ISSUE_COPY` dict in `cold_outreach.py`
3. **(optional)** Update the dashboard's rejection_reason display

### Recommended new rules (high-value, easy to add)

#### Rule: outdated-copyright

A site with "© 2019" in 2026 = the business hasn't updated their website in 5 years. PRIME prospect for "your site needs work" pitch.

```python
import re
import time
current_year = time.gmtime().tm_year

# In _probe_website, after body = r.text.lower():
copyright_match = re.search(r"©\s*(\d{4})", body)
if copyright_match:
    year = int(copyright_match.group(1))
    if year < current_year - 3:  # 3+ years stale
        issues.append("outdated-copyright")
```

In `ISSUE_COPY`:
```python
"outdated-copyright": {
    "opener": "I noticed {domain}'s footer still says © 2019 — looks like the site hasn't been touched in a few years.",
    "stat": "Sites that haven't been updated in 3+ years signal to Google + visitors that the business is inactive or unreliable",
    "short": "the outdated copyright + stale design",
},
```

#### Rule: default-cms-template

A site using a default WordPress/Wix template without customization = "I bought a domain and never finished" prospect.

```python
default_markers = (
    "twentynineteen", "twentytwenty", "twentytwentyone",
    "wp-content/themes/default",
    "wix-static-html-from-the-cloud",
    "weebly-default",
    "godaddysites.com",
)
if any(m in body for m in default_markers):
    issues.append("default-template")
```

In `ISSUE_COPY`:
```python
"default-template": {
    "opener": "I loaded {domain} and it's running on a default template that's never been customized — looks like the site was set up and forgotten.",
    "stat": "Default templates rank ~30% worse in Google for local-business searches because they lack the unique-content signals",
    "short": "the un-customized default template",
},
```

#### Rule: aggressive-popup

Sites with chat widgets, GDPR overlay, newsletter popup, exit intent = annoying UX.

```python
popup_markers = (
    "intercom-app", "drift-widget", "olark-widget",
    "newsletter-popup", "exit-intent", "subscribe-overlay",
    'class="popup-modal"', "lightbox-overlay",
)
popup_count = sum(1 for m in popup_markers if m in body)
if popup_count >= 2:  # multiple popups = bad
    issues.append("popup-heavy")
```

#### Rule: missing-business-info

Many local-business sites lack the basics. Detect missing phone/address mentions = poor SEO.

```python
has_phone_pattern = bool(re.search(r"\(\d{3}\)\s*\d{3}-\d{4}|\d{3}-\d{3}-\d{4}", body))
has_address = bool(re.search(r"\d+\s+\w+\s+(street|st|avenue|ave|road|rd|blvd|drive|dr)", body))
if not has_phone_pattern and not has_address:
    issues.append("missing-nap")  # Name, Address, Phone
```

### Pipeline impact of adding rules

Each new rule:
- Slows the probe by maybe 5ms (regex matching)
- Increases TARGETABLE count (more prospects classified as "bad-website")
- Needs a matching `ISSUE_COPY` entry or the email opener falls through to generic

For SiteBoost, 5-10 well-tuned rules outperform 20 noisy ones. Quality > quantity.

## 5. Stripe Integration — Path to Taking Payments

You're not selling SiteBoost prospects directly to Stripe — you're charging YOUR CUSTOMERS (the local businesses who say yes) after they reply.

### Two flows you'll want

**Flow A — Initial $297 charge** (when a customer says "yes do it"):
1. You send them a Stripe Payment Link (one-time, $297, USD)
2. They click + pay
3. Webhook fires to your app → marks customer as paid → triggers your fulfillment workflow

**Flow B — Recurring $49/mo subscription** (after fulfillment):
1. Stripe Subscription created at customer's start date
2. Auto-charges every month
3. Webhook fires on each renewal → you confirm site is still live; if customer cancels, your fulfillment workflow takes the site offline

### Required env vars (already partial)

```text
STRIPE_API_KEY            ✗ NOT SET — need Stripe Secret key (sk_live_...)
STRIPE_WEBHOOK_SECRET     ✓ SET (already in your env, length 64)
```

Set Stripe API key with secure-paste:
```bash
read -s STRIPE_KEY
railway variables --service wheellsverse-v2 --set "STRIPE_API_KEY=$STRIPE_KEY"
```

### Existing scripts (built but not run live)

There's already a Stripe setup script: `scripts/siteboost_stripe_setup.py`. Run with `--dry-run` first to preview what it would create:

```bash
cd ~/wheellsverse_bots
python scripts/siteboost_stripe_setup.py --dry-run
```

If the dry-run output looks right, run without `--dry-run` to actually create products on your Stripe account:
```bash

```

This creates 7 SKUs:
- $297 one-time site fix
- $49/mo Care plan (recurring monthly)
- $99/mo Growth plan (recurring monthly)
- $497 premium one-time
- $97/mo Premium recurring
- $0 trial trigger (for free intake)
- $25 site review one-time

Output: payment-link URLs written to `data/launches/siteboost/stripe_payment_links.json`.

### Webhook handler (already wired)

`core/api.py` has Stripe webhook routes for handling `payment_intent.succeeded` events. After running the setup script, when a customer pays:

1. Stripe → webhook → your server
2. Verify signature with `STRIPE_WEBHOOK_SECRET`
3. Extract customer email + amount
4. Add to onboarding queue → kickoff `core/siteboost_onboarding.py`

### Onboarding flow (already wired)

`core/siteboost_onboarding.py` handles post-payment fulfillment:
1. Send customer "welcome + intake" email with a link to `local_prospect/intake.html`
2. Collect their business details (logo, color preferences, social links)
3. Generate the final HTML site from their intake data
4. Deploy it to Cloudflare Pages or similar (~1 command)
5. Email the customer the live URL + handoff instructions

### What you need to do once

1. Set `STRIPE_API_KEY` on Railway (one-time)
2. Run `python scripts/siteboost_stripe_setup.py` once to create products
3. Wire the payment-link URL into your reply templates so when customers say "yes", you can drop the link instantly
